# Samsung Galaxy S20 FE: sub-OS security architecture dissected

The Galaxy S20 FE implements a **seven-layer defense-in-depth architecture** spanning immutable boot ROM, hardware secure elements, TrustZone-based TEE, a hypervisor-enforced kernel protector, and file-based encryption — all unified under Samsung's Knox 3.x platform. Critically, the S20 FE predates Knox Vault (introduced with the S21), making its TrustZone TEE and the discrete **S3K250AF secure element chip** the primary hardware trust anchors. Publicly disclosed research has revealed exploitable flaws at every layer — from IV reuse in the Keymaster trusted application affecting ~100 million devices, to zero-click baseband RCE in the Exynos modem requiring only a phone number. This report details the architecture, the attacks, and the forensic landscape as understood through published research.

## Two chipsets, divergent security tradeoffs

The S20 FE ships in two SoC variants with meaningfully different security architectures. The 4G model (SM-G780F) uses Samsung's **Exynos 990**, while all 5G models (SM-G781B/U/W) and a later 4G revision (SM-G780G) use Qualcomm's **Snapdragon 865**. International markets (Europe, Asia, Middle East) predominantly received Exynos; the US, Canada, and Korea received Snapdragon.

The Exynos 990 integrates several Samsung-proprietary security primitives: an **Integrated Secure Element (iSE)** for isolated credential storage, a **Physically Unclonable Function (PUF)** that generates device-unique keys from silicon manufacturing variations, a **DRAM encryption engine** that encrypts all external memory contents in hardware, and a **Stage-2 Memory Protection Unit (S2MPU)** for DMA isolation. Its TEE runs **Samsung TEEGRIS v4.1.0.0**, certified by GlobalPlatform at AVA_TEE.2 assurance level (evaluated by Thales ITSEF, September 2020). The Exynos 990 pairs with a discrete **Exynos Modem 5123** for 5G connectivity — the same modem later found to contain 18 zero-day vulnerabilities by Google Project Zero.

The Snapdragon 865 brings Qualcomm's **Secure Processing Unit (SPU) v4.0**, an on-die hardware sub-chip functioning as a standalone secure subsystem with its own ROM, RAM, CPU, OTP memory, cryptographic accelerators, and countermeasure sensors. The SPU holds **CC EAL4+** and **FIPS 140-2 Level 2** certifications (certificate #3787), making it functionally equivalent to a discrete smartcard. Its TEE runs **Qualcomm Secure Execution Environment (QSEE/QTEE)**. The integrated **Snapdragon X55** modem benefits from Qualcomm's more mature SMMU-based isolation architecture.

Both variants share a discrete **Samsung S3K250AF** secure element chip (CC EAL5+ certified) outside the SoC, plus a **Thales Connected eSE/eSIM** single-chip solution (CC EAL6+, the highest mobile certification level) — the Galaxy S20 was the first phone to feature this combined Thales chip. The Snapdragon variant arguably holds a marginal security advantage due to the SPU's independent certification and Qualcomm's more extensively audited modem isolation, though the Exynos variant's PUF-based key derivation and hardware DRAM encryption offer unique protections against physical attacks.

## Knox 3.x on the S20 FE: TIMA, RKP, and the warranty fuse

Samsung Knox on the S20 FE operates as a three-tier platform. **Knox Base** encompasses hardware root of trust, secure boot, and runtime protections. **Knox Platform for Enterprise** provides 1,500+ management APIs. **Knox Cloud Solutions** delivers remote management services. The sub-OS security story lives entirely in Knox Base.

**TIMA (TrustZone-based Integrity Measurement Architecture)** is Samsung's patented framework running inside the Secure World. It performs Trusted Boot measurement — recording cryptographic hashes of all boot components into tamper-resistant TrustZone memory — and provides runtime integrity monitoring through **Periodic Kernel Measurement (PKM)**, which continuously verifies kernel code and read-only data sections from the Secure World. TIMA's measurements gate access to the Knox Keystore: keys are only released if boot measurements match expected values. TIMA also powers **Knox Device Health Attestation**, a nonce-based protocol where the Secure World generates a signed integrity blob using the device-unique **Samsung Attestation Key (SAK)**, which Samsung's servers validate to produce a cryptographic verdict about device integrity.

**Real-time Kernel Protection (RKP)** is the most architecturally significant Knox component. It runs as a micro-hypervisor ("uH" or "H-Arx") at **ARM Exception Level 2 (EL2)**, positioning it above the Linux kernel (EL1) in the privilege hierarchy. RKP strips the kernel of direct permission to modify memory page tables — any request to mark memory as executable or writable must pass through RKP for approval. It intercepts critical system control instructions, removing them from the kernel's execution path and emulating them only through RKP-approved channels. **Kernel Data Protection (KDP)** enforces hypervisor-level Data Flow Integrity, making sensitive kernel structures read-only: page tables, `struct cred`, `struct task_security_struct`, `struct vfsmount`, and SELinux status variables. Samsung also implements JOPP (JOP Prevention) and ROPP (ROP Prevention) to harden control flow. Early RKP versions shipped as a monolithic `vmm.elf` in the kernel; by the S20 era, it was a separate `uh.bin` binary in the bootloader partition with a "GREENTEA" header, stripped symbols, and obfuscated strings.

The **Knox Warranty Bit** is a one-time programmable eFuse that permanently records device tampering. It transitions from 0x0 to 0x1 and **cannot be reversed** — not by factory reset, not by firmware reflash, only by motherboard replacement. Triggers include booting a non-Samsung-signed kernel, rooting, disabling SELinux, or flashing custom firmware. Once set, device-bound KeyStore data becomes permanently inaccessible because the warranty bit value is incorporated into the key derivation for wrapped keys. Samsung Pay, Secure Folder, and Knox Workspace are permanently disabled. Separate **rollback prevention fuses** encode the minimum acceptable firmware version in hardware, preventing downgrade to older vulnerable bootloaders.

## Inside TrustZone: TEEGRIS, QSEE, and the secure world stack

The ARMv8 exception level layout on the S20 FE places the **Secure Monitor** at EL3 (ARM Trusted Firmware in Samsung's `sboot.bin`), the **TEEGRIS/QSEE kernel** at S-EL1, **Trusted Applications** at S-EL0, the **RKP hypervisor** at EL2, the **Linux kernel** at EL1, and **Android apps** at EL0. World switching occurs via Secure Monitor Call (SMC) instructions, which can only be invoked from EL1 or above — Android userspace cannot directly trigger them. Communication flows through Samsung's GlobalPlatform-compliant TEE Client API (`libteecl.so`), through the kernel's SMC handler, to the Secure Monitor, which saves CPU context and transitions to the TEE kernel, which schedules the target Trusted Application.

On the Exynos variant, **TEEGRIS** is a full TEE kernel (not a microkernel) supporting multicore and multithreading. TAs are loaded in two ways: boot-time TAs bundled in `startup.tzar` (including TSS for shared memory management, ACSD for TA authentication, and `root_task` as the TEE init process), and runtime TAs loaded from `vendor/tee` and `system/tee`. On the Snapdragon variant, **QSEE** loads trustlets at runtime via the `qseecom` kernel driver, with TA verification using a hash table segment and an eFuse-burned root certificate hash.

Key Trusted Applications running in the Secure World include **Keymaster** (hardware-backed key generation using AES, RSA, ECDSA, HMAC; wraps key blobs with a Hardware-Derived Key using AES-GCM-256), **Gatekeeper** (PIN/password authentication with brute-force throttling, returning auth tokens to Keymaster), **TIMA TAs** (integrity measurement, attestation, keystore binding), **Widevine DRM** and **HDCP** TAs for content protection, biometric TAs for fingerprint and face recognition, and Samsung Pay's Trusted UI TA. When Trusted UI is invoked, the TEE reconfigures the **TZASC (TrustZone Address Space Controller)** to make a DRAM region secure for the framebuffer and uses the **TZPC (TrustZone Protection Controller)** to mark display and touch controllers as secure peripherals — preventing even a compromised kernel from reading PIN entry.

TEEGRIS implements exploit mitigations including XN (Execute Never), ASLR, and stack canaries. However, Riscure's 2020 research demonstrated all of these could be bypassed through chaining on the Galaxy S10, which shares the same architecture.

## The secure boot chain from power-on to Android

The boot sequence differs slightly by SoC. On Snapdragon: **Boot ROM (PBL)** → **XBL (eXtensible Bootloader, UEFI)** → **TrustZone + RKP hypervisor** → **ABL (Android Bootloader)** → **Kernel + initramfs** → **dm-verity** → **Android Init** → **Zygote**. On Exynos: **Boot ROM (PBL)** → **S-BOOT** → **TrustZone + RKP** → **Kernel** → **dm-verity** → **Android**.

The PBL resides in **immutable ROM** on the SoC — the ultimate root of trust. It verifies the next stage using the **Samsung Secure Boot Key (SSBK)**, an asymmetric key pair whose public component is burned into **one-time programmable (OTP) fuses** during manufacturing. Samsung holds the private key and uses it to sign all boot components. Each subsequent stage cryptographically verifies the next: if any verification fails, **boot terminates**. The secondary bootloader initializes core hardware, loads and verifies TrustZone, the RKP hypervisor, and then the Android bootloader.

**Trusted Boot** complements Secure Boot by recording measurements (cryptographic hashes) of every boot component into tamper-resistant TrustZone memory. These measurements are used at runtime to gate security-critical operations: releasing Knox Keystore keys, launching Work profile containers, and generating attestation reports. **Knox Verified Boot (KVB)**, introduced with Knox 3.3, extends Android Verified Boot to validate earlier bootloaders — not just the kernel and platform — and ensures all components belong to the same expected build.

**dm-verity** protects system partitions using a Merkle hash tree: the system image is split into 4KB blocks, each assigned a SHA-256 hash, with layers of hashes building to a single root hash verified by an RSA-2048 key on the boot partition. Samsung enhanced stock Android's dm-verity with file-level verification support and Forward Error Correction using Reed-Solomon codes.

Three factory-provisioned hardware keys anchor the entire chain: **DUHK (Device-Unique Hardware Key)**, a symmetric key accessible only by the hardware crypto module and never exposed to software; **SSBK**, the asymmetric boot verification key in OTP fuses; and **SAK (Samsung Attestation Key)**, an ECDSA key pair encrypted by DUHK, whose public key is signed by Samsung's root key via X.509 certificate chain to prove Samsung manufacture.

## File-based encryption and TEE-managed key hierarchy

The S20 FE uses **File-Based Encryption (FBE)**, mandatory for devices launching with Android 10+. Each file is encrypted independently with **AES-256-XTS** using unique per-file keys. The key hierarchy splits into two domains. **Credential Encrypted (CE)** storage keys are derived from the user's PIN/pattern/password combined with a hardware device key, protected by the Keymaster TA in TrustZone, and rate-limited by Gatekeeper. CE keys are only available **after first unlock (AFU)** — the critical forensic boundary. **Device Encrypted (DE)** storage keys derive from hardware keys alone and are available immediately at boot, enabling Direct Boot functionality for alarms, accessibility services, and system processes.

Inside TrustZone, the Keymaster TA wraps all key material using a **Hardware-Derived Key (HDK)**, itself derived from the **Root Encryption Key (REK)** — a device-unique key accessible only through the hardware crypto engine via TEEGRIS's `dev://crypto` driver. For key blobs up to 4,096 bytes, wrapping uses hardware-accelerated AES-GCM-256 (`TEES_WrappedWithREK`); larger blobs fall back to software AES-GCM using the SCrypto library (based on BoringSSL). Encrypted key blobs are passed to the Normal World for filesystem storage, but are useless without the TEE's hardware-bound decryption capability.

**Sensitive Data Protection (SDP)** adds another layer: selected files remain encrypted at runtime, with decryption keys **ejected** each time the device or Knox Workspace locks. SDP uses asymmetric encryption so new data (incoming emails, for example) can be encrypted with the public key even while the private key is unavailable. **DualDAR encryption** applies two independent FIPS 140-certified encryption layers for NSA CSfC compliance.

## Publicly disclosed vulnerabilities paint a sobering picture

The most architecturally significant finding is **CVE-2021-25444 and CVE-2021-25490**, discovered by Shakevsky, Ronen, and Wool at Tel Aviv University and presented at **USENIX Security 2022** ("Trust Dies in Darkness: Shedding Light on Samsung's TrustZone Keymaster Design"). The researchers reverse-engineered the Keymaster TA across Galaxy S9–S21 and found that Samsung's key wrapping used **AES-GCM with a reused IV** — a catastrophic cryptographic error that allowed decryption of hardware-protected key blobs. CVE-2021-25490 enabled a **downgrade attack** forcing S10/S20/S21 devices to generate legacy v15 key blobs vulnerable to the IV reuse flaw. Approximately **100 million Samsung devices** were affected. Samsung's patch removed the entire legacy blob implementation.

Google Project Zero's **March 2023 disclosure of 18 zero-day vulnerabilities** in Samsung's Exynos modems represents the most severe remote attack surface. Four critical bugs — **CVE-2023-24033, CVE-2023-26496, CVE-2023-26497, CVE-2023-26498** — enabled **internet-to-baseband remote code execution requiring only the victim's phone number**, with no user interaction. The **Exynos Modem 5123** used in S20 FE Exynos variants was directly affected. Project Zero took the exceptional step of delaying disclosure of the four most severe bugs. The Shannon baseband's weak exploit mitigations — static stack cookies, no ASLR, disabled MMU features — made exploitation straightforward.

**CVE-2024-44068**, a use-after-free in Exynos processors including the **Exynos 990**, was discovered by Google TAG being **actively exploited in the wild** as part of an advanced attack chain enabling privilege escalation and remote code injection. This directly affects all S20 FE Exynos variants.

Riscure's 2020 research on the Galaxy S10 (same TEEGRIS architecture as S20) demonstrated a **full TEE compromise chain**: HDCP TA exploitation → ASLR bypass → stack canary bypass → kernel driver abuse for physical memory mapping → TZASC register manipulation → TEE memory unprotection → hypervisor page table modification → **full read/write of all TEE memory from an Android app**. The root cause was coarse-grained permissions allowing the HDCP TA to map security-critical registers. Critically, the researchers found that **anti-rollback was not enforced for Trusted Applications**, allowing old vulnerable TAs to be loaded even after patching. A 2024 USENIX Security study confirmed this finding: the WVDRM TA rollback counter on the **S20 was never increased**, leaving it permanently vulnerable to rollback attacks.

Other notable research includes Quarkslab's **Black Hat USA 2020** demonstration of arbitrary code execution in Samsung's S-Boot on Galaxy S8/S9/S10 via USB download mode (SVE-2019-15230); Di Shen's **Black Hat USA 2017** full Knox 2.6 bypass on Galaxy S7 Edge with zero privilege; Gal Beniamini's **Project Zero 2017** work bypassing RKP on Galaxy S7 Edge through KASLR defeat and register manipulation; and Maddie Stone's **Project Zero 2022** analysis of a three-bug in-the-wild exploit chain (CVE-2021-25337/25369/25370) attributed to a commercial surveillance vendor targeting Samsung S10/A50/A51.

## How forensic tools approach the S20 and what limits them

Mobile forensics companies treat **security patch level as the single most critical variable**. Samsung's **March 2022 firmware update** blocked exploits used by major forensic tools; devices on earlier patches remain significantly more accessible.

**Cellebrite UFED** supports logical, advanced logical, full file system (FFS), and physical extraction for the S20 series. Cellebrite Advanced Services (CAS), their premium lab service, can perform PIN/pattern/password determination and full file system extraction from locked S20 devices, including Secure Folder access — though capability depends heavily on firmware version. **GrayKey** (Grayshift/Magnet Forensics) launched Android support specifically with the Samsung S20 and supports passcode brute-force on both Exynos and Snapdragon chipsets, claiming same-day access and up to **10x faster brute-force speeds** on certain Samsung models. **MSAB XRY Pro** supports brute-forcing and FFS extraction for locked Samsung devices; their Advanced Acquisition Lab explicitly supports S20 Qualcomm variants.

The **AFU vs. BFU distinction** is forensically decisive. In After-First-Unlock state, CE encryption keys remain in memory, and forensic tools can access approximately **95% of available data**. In Before-First-Unlock state, most user data remains encrypted — only Device Encrypted storage (system data, some notifications) is accessible. Samsung's **auto-restart feature** in One UI 7+ forces devices back to BFU state after a period of inactivity, specifically designed to counter forensic AFU exploitation. The forensic imperative is keeping seized devices powered on.

**Passware Kit Mobile 2026** introduced a proprietary method for unlocking and decrypting **Exynos-based S20/S21** devices (Exynos 990 and 2100) with security patch levels through April 2025. This does not cover Snapdragon variants. A particularly significant finding, the **"Chip Chop"** research presented at Forensic Focus, demonstrated full forensic acquisition of modern Samsung devices through a two-phase attack: first compromising the Rich Execution Environment to gain root, then exploiting a **single buffer overflow in the CC EAL5+-certified S3K250AF secure element** to bypass PIN verification and transition a device from BFU to AFU state in approximately 90 seconds — without knowing the user's credentials. Samsung patched this vulnerability after responsible disclosure.

**Chip-off forensics is ineffective** against the S20 FE. Samsung devices from the S7 onwards are encrypted by default, and removing the flash chip separates it from the TEE and secure element hardware needed for decryption, rendering extracted data an unreadable encrypted blob. Standard Qualcomm EDL exploitation is also largely inapplicable — Samsung devices lack standard EDL entry methods and no public EDL loaders exist for Samsung. Forensic vendors rely on **proprietary Samsung engineering boot images** that are not publicly available.

## Bootloader unlock: what it costs and who can do it

The bootloader unlock landscape is defined by regional restrictions. International Exynos variants (Europe, Asia) support standard OEM Unlock. **US carrier-locked Snapdragon variants are permanently locked** — the OEM Unlock toggle is disabled or absent. US factory-unlocked models vary by firmware version. Samsung's **VaultKeeper** service on newer devices adds server-side validation, rejecting unofficial partitions until VaultKeeper acknowledges the unlock state after the device connects to the internet.

Enabling OEM Unlock in Developer Options is a prerequisite but does not itself unlock the bootloader — it merely permits the unlock when requested in Download Mode. The actual unlock triggers a **mandatory factory reset**, performing cryptographic erasure of all user data by destroying encryption keys. A critical nuance: **simply unlocking the bootloader does not trip the Knox warranty fuse**. The eFuse is triggered when custom binaries are actually flashed — TWRP, Magisk-patched boot images, custom ROMs, or unsigned kernels. Once tripped, relocking the bootloader with stock firmware is technically possible but the Knox eFuse remains permanently set, and all Knox-dependent functionality remains disabled.

The Knox warranty bit's integration into the key derivation for device-bound wrapped keys means that tripping it causes **immediate and permanent loss of access** to Work profile container data, Secure Folder contents, and all device-bound KeyStore entries. This creates an irreversible forensic dead-end for any Knox-protected data on a device whose fuse has been blown.

## Conclusion

The S20 FE's security architecture represents a genuinely layered defense, but published research reveals that no layer is impenetrable. The most consequential architectural weakness is the **trust placed in TrustZone TAs that store their binaries in the Normal World** — enabling rollback attacks that Samsung has failed to fully mitigate even years after disclosure (the S20's WVDRM TA rollback counter was never incremented). The Keymaster IV reuse vulnerability demonstrated that even hardware-backed cryptography fails when the software implementing it makes elementary cryptographic errors. The Exynos modem's weak exploit mitigations and the resulting zero-click RCE vulnerabilities represent the most dangerous remote attack surface. For forensics, the **security patch level** — not the hardware generation — is the dominant factor determining extractability, with Samsung's March 2022 patch representing a major inflection point. The S20 FE sits at an interesting architectural boundary: it has the discrete S3K250AF secure element that later devices build Knox Vault around, but lacks Knox Vault's dedicated processor and encrypted bus architecture, making its TrustZone implementation the primary — and most researched — trust boundary.
